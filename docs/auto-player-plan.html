Auto-Player: an ephemeral "keep playing similar songs" radio

1 What the feature is, and the unsolved part

The request, verbatim and then distilled into the one thing nobody has cracked yet.

The request: An "auto player" that, when turned on, automatically keeps appending similar songs to the playlist as you listen — streamed ephemerally, never downloaded. The hard part the user can't figure out: how to FIND these "similar" songs. "Similar" does not mean remixes — not "reverbed" or "slowed + reverb" versions of the same song. It means similar in genre / mood / artist style. The user is unsure how similarity should even be defined or detected.

What already works in your favor

The queue already holds ephemeral stream items (source.kind:"stream") with lazy URL resolution via yt-dlp -g. resultToStreamItem + addToQueue are the exact shape an auto-appended track takes — no new data model, no new playback machinery, no download path. Ephemeral teardown is free (drop from the array). Settings persistence is forward-compatible, so an on/off flag is safe to add.

The core unsolved question

There is zero similarity-bearing data anywhere in the app. Song and SearchResult carry only title/artist/duration/thumbnail — no genre, mood, tags, BPM, or embeddings. Worse, the one "artist"-looking field is really the YouTube uploader/channel (often "T-Series", "…- Topic", a random re-uploader). The only discovery primitive is a free-text ytsearch20, and searching by title/artist surfaces exactly the slowed+reverb remixes the user wants to avoid. There is no related / radio / recommendation backend command at all.

Every approach below is, at heart, a different answer to: where does the "similar" signal come from (YouTube's own mix graph, an external metadata graph, local string heuristics, the audio waveform itself, or an LLM's cultural map) — and how it avoids the remix trap.

2 How an auto-appended ephemeral song travels

Same skeleton for every approach: a low-water trigger fires discovery, candidates are de-duped and remix-filtered, survivors become ephemeral stream items appended to the live queue. Only the green "discovery" box differs per approach.

Orange dashed = the timing constraint: if crossfade is on, the next "similar" track must already be in the queue (ideally URL-resolved) before the ~5s fade arm, or the session ends with a hard stop instead of a fade. That forces a prefetch-ahead design — append while >5s of buffer remains, not at "ended".

⛔ Blockers — these must be resolved for the feature to exist at all

  • blocker
    No related/similar discovery capability exists anywhere. The only primitive is free-text search() via ytsearch20. A new Tauri command (e.g. related/radio(videoId)) must be added and registered in lib.rs. ytdlp.rs · lib.rs · api.ts
  • blocker
    Zero similarity-bearing metadata in the data model. Song/SearchResult carry no genre/mood/tags/BPM/embeddings, and "artist" is unreliable uploader text. Nothing local to compute similarity from. types.ts: Song L11-21 · ytdlp.rs entry_to_result
  • blocker
    Song requires a downloaded file (filePath mandatory). Ephemeral picks cannot be Song/library entries — they must live entirely as queue PlaybackItem stream entries. The feature lives in the queue layer, not the library. types.ts L19 · playback.ts songToItem
  • blocker
    Queue advance has no "auto-extend" hook. next() is synchronous and stops at end-of-queue; appending similar songs is an async network round-trip. The single else { audio.pause() } point is the core integration site and isn't built to await. playerStore.ts next() L172-200

4 Approaches

Five candidate mechanisms. Each defines "similar" differently, sources candidates differently, and trades cost/reliability/effort differently. They share steps ⑤–⑧ of the flow above; they differ only at step ③ (discovery) and how they fight the remix trap.
